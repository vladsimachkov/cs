## 1. Обзор документа

Этот документ описывает подробный технический проект системы холодного хранения ColdStore, с акцентом на:

> **Документы по проектированию модулей**: независимый проект каждого слоя см. в каталоге [modules/](modules/).

1. **Слой протокола**: совместимость с протоколом холодного архива S3 (семантика Glacier)
2. **Метаданные кластера**: долгосрочная цель — персистентность на базе [OpenRaft](https://github.com/databendlabs/openraft) + RocksDB
3. **Слой кэширования данных**: долгосрочная цель — высокопроизводительный кэш в пользовательском пространстве на [async-spdk](https://github.com/madsys-dev/async-spdk)

### 1.1 Текущая этапность реализации и уточнения документа

Чтобы избежать расхождения «проект описан полностью, а реализация — лишь каркас», этот документ разделяет возможности системы на два уровня:

| Этап | Статус | Описание |
|------|------|------|
| **Phase 1 (текущая кодовая база)** | реализовано / покрывается юнит-тестами | Gateway/Scheduler/Metadata/Cache образуют безопасный локальный замкнутый цикл: CRUD корзинок и объектов, PutObject, HeadObject, GetObject, DeleteObject, RestoreObject, ListObjects, staging/restored на HDD Cache, отметка Phase-1 archive и очистка staging — всё покрыто юнит-тестами; Tape по-прежнему не обращается к реальному оборудованию |
| **Phase 2A (текущая работа)** | начато / локальная персистентность | В Metadata добавлен опциональный вход бинарной персистентности snapshot: после перезапуска сервиса восстанавливаются состояния в памяти bucket/object/worker/task/tape и т.д.; на этом этапе это по-прежнему одноузловая локальная персистентность, а не консенсус Raft |
| **Phase 2B (следующая цель)** | цель проектирования | Snapshot/конечный автомат Metadata эволюционируют в state machine OpenRaft + Raft log, бэкенд хранения переключается на RocksDB/openraft-rocksstore; затем добавляются безопасные тесты многоузловой согласованности |
| **Phase 3 (целевая архитектура)** | цель проектирования | Cache поддерживает SPDK; Tape подключается к реальному SCSI/LTFS/SDK вендоров; добавляются межпроцессные интеграционные тесты и проверка на реальном оборудовании |

Принципы проектирования Phase 1:
- не обращаться к реальным ленточным устройствам
- не запускать настоящий распределённый кластер
- не выполнять интеграционные тесты, меняющие внешнее окружение хоста
- сначала довести протокольные объекты, переходы состояний, чтение и запись кэша, CRUD метаданных до проверяемых локальных возможностей

Поэтому в этом документе всё, что касается SPDK и управления реальной ленточной библиотекой, считается **проектом целевого состояния**; всё, что касается локального замкнутого цикла Gateway/Scheduler/Metadata/Cache, считается **проектом текущей реализации Phase 1**; всё, что касается персистентности snapshot в Metadata, считается **проектом текущей работы Phase 2A**; всё, что касается OpenRaft, журнала репликации RocksDB и многоузловой согласованности, считается **проектом целевого состояния Phase 2B**.

### 1.1 Ключевой выбор технологий (определён)

| Компонент | Библиотека/решение | Описание |
|------|---------|------|
| Консенсус Raft | **openraft** | [databendlabs/openraft](https://github.com/databendlabs/openraft), асинхронный Raft на Tokio |
| Хранилище Raft | **openraft-rocksstore** | Бэкенд на RocksDB, RaftLogStorage + RaftStateMachine |

## 2. Общая архитектура системы

### 2.1 Модель физического развёртывания

ColdStore состоит из пяти типов узлов. **Scheduler Worker — единственный бизнес-хаб**,
Gateway подключается только к Scheduler Worker, Console — только к Metadata.

```
┌──────────────────────┐          ┌──────────────────────┐
│  Gateway (N узлов)   │          │  Console (1 узел)    │
│  S3 HTTP фронтенд    │          │  Web UI панели       │
│  без состояния       │          │  без состояния       │
└──────┬───────────────┘          └──────┬───────────────┘
       │ gRPC (адреса Scheduler)         │ gRPC (адреса Metadata)
       ▼                                 ▼
 ┌─────────────────────────────┐  ┌──────────────────────────┐
 │  Тот же физический узел     │  │  Узлы Metadata (3/5 шт)  │
 │  ┌─────────────────────────┐│  │  Консенсус Raft + RocksDB│
 │  │  Scheduler Worker       ││  │  Метаданные + реестр     │
 │  │  бизнес-ядро: оркестрация││  │  Worker                  │
 │  ├─────────────────────────┤│  └──────────────────────────┘
 │  │  Cache Worker           ││             ▲
 │  │  кэш SPDK Blobstore     ││             │ heartbeat
 │  └─────────────────────────┘│  ┌──────────┴───────────────┐
 └─────────────────────────────┘  │  Tape Worker (отдельный  │
                                  │  физический узел)        │
                                  │  Накопители /dev/nst*    │
                                  │  Библиотека /dev/sg*     │
                                  └──────────────────────────┘
```

| Тип узла | Обязанности | Количество | Объекты подключения |
|----------|------|------|----------|
| **Metadata** | Консенсус Raft, хранение метаданных, реестр Worker | 3/5 | heartbeat трёх типов Worker; управление из Console |
| **Scheduler Worker** | **бизнес-хаб**: оркестрация планирования, работа со всеми слоями (на одной машине с Cache) | 1~N | Metadata, Cache Worker, Tape Worker, Gateway |
| **Cache Worker** | Кэш данных SPDK NVMe (на той же машине, что и Scheduler) | 1~N | Scheduler Worker (gRPC), Metadata (heartbeat) |
| **Tape Worker** | Управление ленточными накопителями, чтение и запись данных (отдельный физический узел) | 1~N | Scheduler Worker (gRPC), Metadata (heartbeat) |
| **Gateway** | Доступ через S3 HTTP + адаптация протокола (без состояния) | N | **только Scheduler Worker** |
| **Console** | Web UI панели администрирования + Admin API (без состояния) | 1 | **только Metadata** |

**Ключевые проектные решения**:

- **Gateway не подключается к Metadata напрямую**: Gateway — чистый фронтенд протокола S3, все бизнес-запросы (включая запросы метаданных)
  проксируются через Scheduler Worker. В конфигурации Gateway достаточно указать адреса Scheduler Worker.
- **Scheduler Worker — единственный бизнес-хаб**:хранит MetadataClient, оркестрирует Cache Worker и Tape Worker,
  принимает все запросы Gateway.
- **Console подключается только к Metadata**: панель администрирования напрямую запрашивает/изменяет кластер метаданных и управляет добавлением и удалением Worker.
- **Scheduler ↔ Cache общаются по gRPC**: несмотря на размещение на одной машине, связь идёт по gRPC через сеть,
  что сохраняет единообразие архитектуры и позволяет независимо масштабировать в дальнейшем.

### 2.2 Логическая слоистая архитектура

```
┌─────────────────────────────────────────────────────────────────────────────┐
│              Слой доступа S3 (Axum) — Gateway                               │
│  PUT / GET / HEAD / DELETE / RestoreObject / ListBuckets ...                 │
│                  Слой адаптации протокола холодного архива S3                │
│  Отображение StorageClass | Разбор RestoreRequest | Ответ x-amz-restore | Коды ошибок    │
└─────────────────────────────────────────────────────────────────────────────┘
                                        │ gRPC (все запросы)
                                        ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│         Планировщики архивации/восстановления — Scheduler Worker            │
│      Запросы Gateway │ оркестрация Cache и Tape │ чтение и запись Metadata   │
└─────────────────────────────────────────────────────────────────────────────┘
            │                       │                       │
            ▼ gRPC                  ▼ gRPC (одна машина)    ▼ gRPC (удалённо)
┌───────────────────────┐  ┌───────────────────────┐  ┌───────────────────────┐
│  Кластер метаданных   │  │  Слой кэша (SPDK)     │  │  Слой лент (Tape)     │
│  (Raft)               │  │  Cache Worker         │  │  Tape Worker          │
│  Узлы Metadata        │  │  кэш NVMe в user      │  │  свой SDK + SCSI      │
│  Персистентность      │  │  space                │  │                       │
│  RocksDB              │  │                       │  │                       │
└───────────────────────┘  └───────────────────────┘  └───────────────────────┘
```

### 2.3 Модель взаимодействия

В **целевом состоянии** Scheduler Worker — единственная точка бизнес-чтения и записи метаданных (кроме управления из Console); Gateway, Cache Worker и Tape Worker не обращаются к Metadata напрямую.

В **текущей реализации (Phase 1 + начало Phase 2A)** реально реализованы и проверяются юнит-тестами:
- реализация конечного автомата MetadataService в процессе, покрывающая CRUD и переходы состояний для bucket/object/archive bundle/archive task/recall task/tape/worker registry
- опциональный вход локальной персистентности snapshot в MetadataService: `MetadataServiceImpl::new_with_snapshot(config, path)` сохраняет бинарный snapshot после записи и восстанавливает состояние при перезапуске
- реализация CacheService на локальном HDD-бэкенде, покрывающая запись, чтение, перечисление и удаление данных staging/restored
- безопасный замкнутый цикл Phase 1 для Gateway/Scheduler/Metadata/Cache: операции с корзинами, put/head/get/delete/list объектов, чтение после restore, batch-отметка archive staging как cold с очисткой staging
- Tape Worker по-прежнему не обращается к реальным устройствам `/dev/nst*`/`/dev/sg*`; реальное чтение и запись ленты отнесены на последующие этапы

Иными словами, текущая кодовая база уже проверяет «замкнутый цикл протокола, семантики состояний и локального пути данных» и начала проверять «одноузловую персистентность Metadata»; но «полный распределённый кластер Raft, репликацию согласованности и реальный аппаратный I/O» ещё не проверены.

```
                                Console ──управляющее чтение/запись──▶ Metadata
                                                        ▲
Gateway ──все запросы──▶ Scheduler Worker ──чтение+запись──────────┘
                           │
                           ├──gRPC──▶ Cache Worker   (чистое хранение данных)
                           └──gRPC──▶ Tape Worker    (чистая аппаратная абстракция)
```

| Слой | Отношение к Metadata | Отношение к Scheduler | Описание |
|------|------|------|------|
| Gateway | **прямого подключения нет** | gRPC-клиент | все запросы проксируются в Scheduler |
| Scheduler Worker | чтение + запись | — | единственный бизнес-хаб |
| Cache Worker | только регистрация heartbeat | gRPC-сервер | чистое хранение данных |
| Tape Worker | только регистрация heartbeat | gRPC-сервер | чистая аппаратная абстракция |
| Console | управляющие чтение/запись | нет | добавление и удаление Worker, запросы метаданных |

## 3. Проектирование совместимости с протоколом холодного архива S3

### 3.1 Цели совместимости с протоколом

ColdStore — это **система чистого холодного архива**, её модель совпадает с AWS S3 Glacier Deep Archive:
любой записанный объект сразу ставится в очередь архивации на ленту, онлайн-слой горячего хранения отсутствует. Внешняя система горячего хранения, которой нужен холодный архив, вызывает PutObject API ColdStore; решение о переносе принимает внешняя система.

На уровне протокола обеспечивается совместимость с семантикой холодного архива AWS S3 Glacier, чтобы существующие S3-клиенты, SDK и бизнес-системы подключались без доработок.

### 3.2 Отображение категорий хранения

Во внутреннем состоянии ColdStore всего два значения:

| S3 Storage Class | Внутреннее состояние ColdStore | Описание |
|------------------|-------------------|------|
| любой (`GLACIER` / `DEEP_ARCHIVE` / `STANDARD` и т.д.) | `ColdPending` | запись сразу ставится в очередь архивации (единая точка входа холодного хранилища) |
| архивация завершена | `Cold` | данные заархивированы на ленту |

### 3.3 Спецификация RestoreObject API

#### 3.3.1 Формат запроса

```
POST /{Bucket}/{Key}?restore&versionId={VersionId} HTTP/1.1
Host: {endpoint}
Content-Type: application/xml

<RestoreRequest xmlns="http://s3.amazonaws.com/doc/2006-03-01/">
  <Days>integer</Days>
  <GlacierJobParameters>
    <Tier>Expedited|Standard|Bulk</Tier>
  </GlacierJobParameters>
</RestoreRequest>
```

**Ключевые параметры:**

| Параметр | Обязателен | Описание |
|------|------|------|
| `Days` | да | число дней хранения размороженных данных, минимум 1 день |
| `GlacierJobParameters.Tier` | нет | приоритет восстановления: Expedited / Standard / Bulk |
| `versionId` | нет | версия объекта; по умолчанию текущая версия |

#### 3.3.2 Семантика уровней восстановления (Tier)

| Tier | Ожидаемое время выполнения | Стратегия реализации в ColdStore |
|------|-------------|-------------------|
| **Expedited** | 1–5 минут | очередь высокого приоритета, резервируемая ёмкость настраивается |
| **Standard** | 3–5 часов | очередь по умолчанию, обычное планирование |
| **Bulk** | 5–12 часов | низкий приоритет, пакетное объединённое восстановление |

#### 3.3.3 Спецификация ответа

| Сценарий | HTTP-код | Описание |
|------|------------|------|
| первый запрос разморозки | `202 Accepted` | задача принята, ожидает обработки |
| уже разморожено и не просрочено | `200 OK` | возможно продлить Days, обновляется только срок истечения |
| разморозка выполняется | `409 Conflict` | код ошибки `RestoreAlreadyInProgress` |
| недостаточно ёмкости Expedited | `503 Service Unavailable` | код ошибки `GlacierExpeditedRetrievalNotAvailable` |
| объект ещё не заархивирован | `409 Conflict` | для объекта в состоянии ColdPending Restore невозможен |

### 3.4 HEAD Object и заголовок ответа x-amz-restore

При HEAD для холодного объекта необходимо возвращать заголовок `x-amz-restore`, отражающий состояние разморозки:

```
x-amz-restore: ongoing-request="true"
```
или
```
x-amz-restore: ongoing-request="false", expiry-date="Fri, 28 Feb 2025 12:00:00 GMT"
```

### 3.5 Контроль доступа GET к холодному объекту

| Состояние объекта | Поведение GET |
|----------|----------|
| ColdPending (в очереди) | возвращается `403 InvalidObjectState`, объект ещё не заархивирован |
| Cold + не разморожено | возвращается `403 InvalidObjectState` с указанием сначала выполнить Restore |
| Cold + разморозка выполняется | возвращается `403 InvalidObjectState` |
| Cold + разморожено | данные читаются из кэша SPDK и возвращаются |
| Cold + срок разморозки истёк | возвращается `403 InvalidObjectState`, требуется повторный Restore |

### 3.6 Сопоставление кодов ошибок

| Код ошибки AWS | HTTP-статус | Реализация в ColdStore |
|------------|-----------|----------------|
| `InvalidObjectState` | 403 | GET холодного объекта, который ещё не разморожен |
| `RestoreAlreadyInProgress` | 409 | повторный запрос Restore |
| `GlacierExpeditedRetrievalNotAvailable` | 503 | недостаточно ёмкости Expedited |
### 3.7 Модель запуска архивации

ColdStore — система чистого холодного архива (аналог AWS Glacier Deep Archive): любой объект при записи PutObject помечается как `ColdPending`
и автоматически ставится в очередь ожидания, откуда планировщик агрегирует его и пишет на ленту. Категории хранения Hot/Warm и правила жизненного цикла не поддерживаются.

Внешняя система горячего хранения, которой нужен холодный архив, напрямую вызывает PutObject API ColdStore и записывает объект.
Решение о переносе (когда архивировать) принимает внешняя система; ColdStore жизненным циклом не управляет.

## 4. Метаданные кластера: текущая реализация Phase 1 и целевой проект Phase 2

### 4.0 Текущая реализация (Phase 1)

В текущем коде MetadataService реализован как конечный автомат в процессе и предоставляет следующие проверяемые юнит-тестами возможности:
- CRUD корзинок
- CRUD / List / Head объектов
- обновление StorageClass / RestoreStatus / ArchiveLocation
- базовый CRUD для ArchiveBundle / ArchiveTask / RecallTask / TapeInfo
- регистрация Worker, обновление состояния и heartbeat
- вывод статичного представления в памяти ClusterInfo

Цель этой реализации — не заменить итоговый распределённый кластер метаданных, а:
- заранее зафиксировать контракт protobuf
- проверить переходы состояний и модель объекта
- дать Scheduler / Gateway / Console стабильный mockable backend для будущей интеграции
- обеспечить проверяемость ключевой семантики без подключения RocksDB, Raft и отладки сети

### 4.1 Целевой проект (Phase 2)

### 4.2 Цели проектирования

- **Строгая согласованность**: чтение и запись метаданных проходят через достижение консенсуса Raft
- **Высокая доступность**: сервис доступен, пока живо большинство узлов
- **Персистентность**: RocksDB как движок хранения журнала Raft и конечного автомата
- **Масштабируемость**: поддержка кластеров из 3/5/7 узлов

### 4.3 Выбор технологий (определён)

| Компонент | Выбор | Описание |
|------|------|------|
| Реализация Raft | **openraft** | [databendlabs/openraft](https://github.com/databendlabs/openraft), асинхронный Raft на Tokio |
| Хранилище Raft | **openraft-rocksstore** | [crates.io/openraft-rocksstore](https://crates.io/crates/openraft-rocksstore), бэкенд на RocksDB |
| Движок хранения | RocksDB | через обёртку openraft-rocksstore |

### 4.3.1 Ключевые точки интеграции OpenRaft

- **Зависимости**: `openraft = "0.9"`, `openraft-rocksstore = "0.9"`
- **TypeConfig**: задаются типы `NodeId`, `Node`, `AppData`, `AppDataResponse` и другие
- **RocksRequest**: расширяется `AppData`, определяются команды `PutObject`, `DeleteObject`, `PutRecallTask` и другие
- **RocksStateMachine**: реализуется логика `apply`, записывающая команды в бизнес-CF RocksDB
- **Линейализуемое чтение**: `raft.ensure_linearizable().await` гарантирует чтение зафиксированного состояния

### 4.4 Модель данных RocksDB

#### 4.4.1 Проектирование Column Family

| Имя CF | Формат Key | Формат Value | Описание |
|---------|----------|-----------|------|
| `objects` | `obj:{bucket}:{key}` | ObjectMetadata (JSON/Protobuf) | метаданные объекта |
| `object_versions` | `objv:{bucket}:{key}:{version}` | ObjectMetadata | многоверсионные объекты |
| `bundles` | `bundle:{uuid}` | ArchiveBundle | архивный комплект |
| `tapes` | `tape:{tape_id}` | TapeInfo | сведения о ленте |
| `recall_tasks` | `recall:{uuid}` | RecallTask | задача восстановления |
| `archive_tasks` | `archive:{uuid}` | ArchiveTask | задача архивации |
| `index_bundle_objects` | `idx_b:{archive_id}:{bucket}:{key}` | пусто | обратный индекс «архивный комплект → объект» |
| `index_tape_bundles` | `idx_t:{tape_id}:{bundle_id}` | пусто | индекс «лента → архивный комплект» |

#### 4.4.2 Хранилище журнала Raft (raftdb)

- **Key**: `{log_index}` (8 bytes)
- **Value**: сериализованная запись журнала Raft
- **Назначение**: хранит только журнал консенсуса Raft, отдельно от бизнесового KV

### 4.5 Команды конечного автомата Raft (расширение AppData / RocksRequest)

По образцу модели `RocksRequest` из openraft-rocksstore расширяется набор команд ColdStore:

```rust
// реализация openraft::AppData
#[derive(Clone, Debug, Serialize, Deserialize)]
enum ColdStoreRequest {
    PutObject(ObjectMetadata),
    DeleteObject { bucket: String, key: String },
    UpdateStorageClass { bucket: String, key: String, class: StorageClass },
    PutArchiveBundle(ArchiveBundle),
    PutTape(TapeInfo),
    PutRecallTask(RecallTask),
    UpdateRecallTask { id: Uuid, status: RestoreStatus },
    PutArchiveTask(ArchiveTask),
}
```

Можно расширять `RocksStore` из `openraft-rocksstore` либо реализовать собственный `RaftStorage` с поддержкой перечисленных бизнес-команд.

### 4.6 Пути чтения и записи

| Тип операции | Путь |
|----------|------|
| **запись** | Client → Leader → Propose в Raft → Append к большинству → Apply → запись в RocksDB |
| **чтение** | Client → любой узел → локальное чтение RocksDB (при необходимости ReadYourWrites опционально через Leader) |
| **линейализуемое чтение** | через ReadIndex в Raft, гарантирующее чтение зафиксированного состояния |

### 4.7 Развёртывание кластера

- **Рекомендуемая конфигурация**: 3 или 5 узлов
- **Выбы лидера**: автоматические выборы Raft
- **Сеть**: gRPC или собственный RPC между узлами
- **Путь персистентности**: `/var/lib/coldstore/metadata/{raftdb|kvdb}`

### 4.8 Интеграция с существующим кодом

- Добавляется вариант перечисления `MetadataBackend::RaftRocksDB`
- `MetadataService` проксирует запросы на запись через Raft-клиент
- Запросы на чтение могут обращаться к локальному RocksDB (только для чтения на Follower)

## 5. Слой кэширования данных: текущая реализация Phase 1 и целевой проект Phase 2

### 5.0 Текущая реализация (Phase 1)

В текущем коде CacheService сначала реализован на HDD-бэкенде и отвечает за:
- временное хранение данных PutObject (staging)
- хранение восстановленных данных restored
- Contains / Get / GetStaging / Delete / DeleteStaging / Stats через индекс в процессе
- сканирование локальных файлов метаданных и перестроение индекса при запуске

Текущая реализация сознательно не включает:
- SPDK bdev / blobstore
- настоящий поток планирования стратегии вытеснения кэша
- многоузловую согласованность кэша

Ключевая цель текущего этапа — корректность протокола кэша, индекса объектов, потокового чтения/записи и логики статистики.

### 5.1 Целевой проект (Phase 2)

### 5.2 Цели проектирования

- **Высокая производительность**: I/O в пользовательском пространстве, в обход ядра, с меньшей задержкой
- **Высокая пропускная способность**: режим Poll, нулевое копирование, полное использование возможностей NVMe
- **Кэш размороженных данных**: хранение данных, извлечённых с ленты, для быстрого ответа на GET
- **Нативный async/await**: бесшовная интеграция с Tokio без мостов на колбэки

### 5.2 Выбор технологий: async-spdk + SPDK Blob

Используется [madsys-dev/async-spdk](https://github.com/madsys-dev/async-spdk):

- **Асинхронные привязки для Rust**: нативные `async`/`await` поверх Tokio
- **Способ хранения**: **SPDK Blobstore (Blob)**, а не raw bdev; Blobstore построен поверх bdev
- **Преимущества**: Blob даёт персистентное выделение блоков, метаданные xattrs, thin provisioning — подходит для кэша объектов

### 5.5 Пример конфигурации SPDK JSON

**Тестовый Malloc bdev** (`cache_spdk.json`):

```json
{
  "subsystems": [
    {
      "subsystem": "bdev",
      "config": [
        {
          "method": "bdev_malloc_create",
          "params": {
            "name": "Malloc0",
            "num_blocks": 32768,
            "block_size": 512
          }
        }
      ]
    }
  ]
}
```

**Производственное NVMe**: согласно [async-spdk README](https://github.com/madsys-dev/async-spdk), нужно указать соответствующее имя bdev (например, `Nvme0n1`) и убедиться, что:

- процесс запущен от root
- выделены hugepages: `echo "1024" > /sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages`
- сборка SPDK: `./configure --without-isal` позволяет избежать части ошибок isa-l

### 5.6 Размещение данных кэша (способ SPDK Blob)

| Уровень | Носитель | Назначение |
|------|----------|------|
| L1 | NVMe SSD (SPDK Blobstore on bdev) | горячие размороженные данные, низкая задержка |
| L2 (опционально) | файловая система | совместимость со старой реализацией, тёплые данные |

Соответствие объектов и Blob:

- **1 объект = 1 Blob**: каждая размороженная пара «объект — Blob» соответствует друг другу в Blobstore
- **Метаданные**: в xattrs Blob хранятся bucket, key, size, checksum, expire_at
- **Индекс**: самостоятельно поддерживаемое сопоставление `cache_key → blob_id` (Blobstore не предоставляет поиск по имени)
- **Единица чтения/записи**: Page (4KB), Cluster (1MB) — единица выделения

### 5.7 Стратегии кэша

| Стратегия | Описание |
|------|------|
| **LRU** | вытесняется объект, к которому дольше всего не обращались |
| **LFU** | вытесняется объект с наименьшей частотой обращений |
| **TTL** | вытеснение по сроку истечения разморозки |
| **Ёмкость** | общий предел ёмкости; при превышении запускается вытеснение |

## 6. Слой управления лентами: собственный слой абстракции SDK

### 6.1 Цели проектирования

- **Собственный слой абстракции SDK**: без зависимости от закрытых SDK вендоров, единый интерфейс доступа к лентам, накопителям и библиотекам
- **Первый этап — Linux SCSI**: реализация на драйвере лент SCSI ядра Linux (st/ sg)
- **Расширяемость**: в дальнейшем реализацию можно заменить на SDK вендора, LTFS и т.д. без изменений в логике планирования верхнего слоя

### 6.2 Слоистая архитектура

```
│  - абстракция ленточной библиотеки, планирование накопителей,   │

└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  Слой абстракции Tape SDK (собственная разработка)              │

└─────────────────────────────────────────────────────────────────┘
```

### 6.3 Реализация первого этапа: протокол Linux SCSI

#### 6.3.1 Устройства и интерфейсы

| Интерфейс | Узел устройства | Описание |
|------|----------|------|
| **драйвер st** | `/dev/nst0` | без автоматической перемотки, рекомендуется для последовательного чтения и записи (избегает перемотки на каждой операции) |
| **драйвер st** | `/dev/st0` | автоматическая перемотка, возврат к BOT после операции |
| **SCSI Generic** | `/dev/sg*` | прозрачная передача команд SCSI для расширенного управления (опционально) |

#### 6.3.2 Управляющий интерфейс MTIO

На основе `<sys/mtio.h>`, основные ioctl:

| ioctl | Назначение |
|-------|------|
| `MTIOCTOP` | выполнение ленточных операций: `MTFSF`(вперёд на файл), `MTBSF`(назад на файл), `MTFSR`(вперёд на запись), `MTBSR`(назад на запись), `MTREW`(перемотка), `MTEOM`(к концу тома) |
| `MTIOCGET` | получение состояния накопителя |
| `MTIOCPOS` | получение текущей позиции на ленте |

#### 6.3.3 Чтение и запись данных

- **Блочный режим**: переменный или фиксированный блок (задаётся ioctl)
- **Чтение/запись**: стандартные системные вызовы `read()` / `write()`
- **Последовательность**: на ленту запись ведётся только последовательно; для случайного чтения нужно сначала выполнить seek

#### 6.3.4 Зависимости и утилиты

- `mt-st`: команда mt для управления лентой (опционально, SDK сам выполняет ioctl)
- ядро: модуль `st` (`modprobe st`)
- права: узлы устройств должны быть доступны на чтение и запись (обычно root или группа tape)

### 6.4 Определение абстрактных интерфейсов SDK


## 7. Взаимодействие модулей и потоки данных

### 7.1 Полный процесс Restore

```
1. Client: POST /bucket/key?restore + RestoreRequest
2. S3 Handler: разбор Days/Tier, проверка что объект в состоянии Cold
3. Metadata (Raft): проверка наличия уже идущего Restore, запись RecallTask
4. Recall Scheduler: объединяет задачи по archive_id, планирует чтение ленты
5. Tape: последовательное чтение → блоки данных
6. Cache (SPDK): запись в bdev SPDK, обновление индекса
7. Metadata (Raft): обновление ObjectMetadata.restore_status=Completed, restore_expire_at
8. Client: HEAD показывает x-amz-restore: expiry-date="..."
9. Client: GET возвращает данные из кэша SPDK
```

### 7.2 Полный процесс PutObject

```
1. Gateway: приём запроса S3 PutObject
2. Scheduler Worker: помещение данных в staging на Cache Worker (gRPC: PutStaging)
3. Scheduler Worker: запись в Metadata (Raft: PutObject, storage_class=ColdPending, staging_id)
4. Gateway: возврат 200 OK
```

### 7.3 Полный процесс Archive

```
1. Archive Scheduler: сканирование объектов ColdPending, получение staging_id
2. Archive Scheduler: чтение данных из staging на Cache Worker (gRPC: GetStaging)
3. Archive Scheduler: агрегация в ArchiveBundle по стратегии
4. Tape: последовательная запись на ленту
5. Metadata (Raft): запись ArchiveBundle, обновление ObjectMetadata (Cold, archive_id, tape_id, очистка staging_id)
6. Cache Worker: удаление staging-данных (gRPC: DeleteStaging)
```
