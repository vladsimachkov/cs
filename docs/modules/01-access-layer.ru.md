# Проектирование модуля слоя доступа

> Архитектура: система холодного хранения ColdStore  
> См. также: [Проектирование общей архитектуры](../DESIGN.ru.md)

## 1. Обзор модуля

Слой доступа — это точка входа, через которую ColdStore предоставляет вовне объектное хранилище. Он отвечает за приём и распределение S3-совместимых HTTP-запросов.

### 1.1 Обязанности

- Предоставлять HTTP-сервис, слушающий эндпоинт S3
- Разбор маршрутов: распределять запросы по соответствующим обработчикам
- Проксирование запросов/ответов и базовая валидация
- Взаимодействие со слоем адаптации протокола, метаданными, кэшем и планировщиком

### 1.2 Место в архитектуре

```
                    ┌─────────────────────────────────────┐
                    │  Уровень доступа S3 (этот модуль)   │
                    │  PUT / GET / HEAD / RestoreObject   │
                    │  ListBuckets / DeleteObject         │
                    └─────────────────────────────────────┘
                                        │
                                        ▼
        Слой адаптации протокола / метаданные / кэш / планировщик
```

## 3. Перечень интерфейсов

### 3.1 Операции с объектами

| Метод | Путь | Описание |
|------|------|------|
| PUT | `/{bucket}/{key}` | Загрузка объекта |
| GET | `/{bucket}/{key}` | Скачивание объекта |
| HEAD | `/{bucket}/{key}` | Получение метаданных объекта |
| DELETE | `/{bucket}/{key}` | Удаление объекта |
| POST | `/{bucket}/{key}?restore` | Разморозка холодного объекта (RestoreObject) |

### 3.2 Операции с корзинами

| Метод | Путь | Описание |
|------|------|------|
| GET | `/` | ListBuckets |
| PUT | `/{bucket}` | CreateBucket |
| GET | `/{bucket}` | ListObjects |
| DELETE | `/{bucket}` | DeleteBucket |

### 3.3 Правила маршрутизации

- Параметры пути: `bucket`, `key` (поддерживаются многоуровневые key)
- Параметры запроса: `versionId`, `restore` и другие
- Необходимо поддерживать как виртуальный хост-стиль, так и путь-стиль (настраивается)

## 4. Структура модуля

```
src/
├── main.rs              # запуск Axum, загрузка конфигурации
├── s3/
│   ├── mod.rs
│   ├── server.rs        # определение Axum Router, регистрация маршрутов
│   ├── handler.rs       # точка обработки запросов, делегирование адаптации протокола/бизнес-логике
│   └── routes.rs        # константы маршрутов, разбор путей
```

---

## 5. Зависимости

| Зависимый модуль | Способ связи | Назначение |
|----------|----------|------|
| Слой адаптации протокола | локальный вызов (в том же процессе) | разбор RestoreRequest, формирование ответа x-amz-restore, сопоставление кодов ошибок |
| Scheduler Worker | gRPC (адрес из конфигурации) | проксирование **всех** бизнес-запросов (PUT/GET/HEAD/DELETE/Restore/List) |

> Gateway **не подключается к Metadata** и **не подключается к Cache Worker и Tape Worker**.
> Весь бизнес-трафик идёт через Scheduler Worker. Gateway — это чистый фронтенд протокола S3 HTTP → gRPC.

## 6. Параметры конфигурации

```yaml
gateway:
  s3:
    host: "0.0.0.0"
    port: 9000
    path_style: true

  # достаточно указать только адреса Scheduler Worker
  scheduler_addrs:
    - "10.0.2.1:22001"
    - "10.0.2.2:22001"

  # стратегия маршрутизации при нескольких Scheduler Worker
  routing:
    strategy: "round_robin"   # round_robin | hash | least_pending
```

## 7. Нефункциональные требования

- **Отсутствие состояния**: горизонтальное масштабирование, несколько экземпляров + балансировка нагрузки
- **Наблюдаемость**: трассировка запросов, длительность, доля ошибок
- **Безопасность**: поддержка подписи S3 v4, TLS
