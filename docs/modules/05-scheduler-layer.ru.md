# Проектирование модуля слоя планирования архивации и восстановления

> Архитектура: система холодного хранения ColdStore  
> См. также: [Проектирование общей архитектуры](../DESIGN.ru.md)

## 1. Обзор модуля

Слой планирования архивации и восстановления отвечает за планирование архивации и извлечения холодных данных и является слоем бизнес-логики ColdStore. При проектировании необходимо учитывать **последовательный характер чтения и записи ленты**: стратегии агрегации и объединения максимизируют пропускную способность и сокращают число перестановок ленты и seek.

### 1.0 Текущее состояние реализации (безопасный базовый уровень Phase-1)

В текущем коде есть безопасный проверяемый юнит-тестами срез пакетной архивации:

- `MetadataBackedSchedulerBackend::archive_staging_batch(cache, tape, limit)` выполняет пакет архивации через внедряемые `Phase1ArchiveCache` и `TapeArchiveWriter`, не обращаясь напрямую к устройствам хоста.
- `CacheArchiveClient` уже адаптирует настоящий gRPC-клиент `CacheService` под `Phase1ArchiveCache`; юнит-тесты проверяют list/get/delete в staging на in-process CacheService с временным HDD-бэкендом, а не только на fake cache.
- `TapeArchiveClient` уже адаптирует настоящий gRPC-клиент `TapeService` под `TapeArchiveWriter`; юнит-тесты проверяют запись filemark в `WriteBundle` и чтение обратно в `ReadBundle` на in-process TapeService с backend-симулятором, а не прямым вызовом helper сервиса.
- Этот срез читает staging-данные, вызывает writer ленты для записи bundle, записывает `ArchiveBundle`, затем обновляет у объекта `archive_id` / `tape_id` / `tape_set` / `tape_block_offset` и `StorageClass::Cold`, после чего удаляет staging-данные.
- Юнит-тесты используют in-process writer / gRPC-клиент `coldstore-tape` симулятора, чтобы проверить настоящую запись filemark и чтение обратно; mhVTL не запускался, `/dev/*` не использовались.
- Сейчас один staging-объект соответствует одному Phase-1 bundle (`phase1-bundle:<bucket>/<key>`); агрегация нескольких объектов, выбор накопителя, компенсация сбоев и клиент живого tape worker отнесены на последующие этапы.

> **Модель развёртывания**: слой планирования работает на узлах **Scheduler Worker** и является **единственным бизнес-хабом** ColdStore.
> Все S3-запросы Gateway обрабатываются Scheduler Worker.
> Scheduler через gRPC связан с Cache Worker (та же машина) и Tape Worker (удалённо),
> а также читает и пишет кластер Metadata по gRPC. Cache/Tape Worker не принимают запросы Gateway напрямую.
>
> **Принцип координации записи метаданных (вариант B)**: Scheduler Worker — **единственная бизнес-точка** чтения и записи метаданных.
> Gateway к Metadata напрямую не подключён. Слой кэша и слой лент MetadataClient не хранят,
> все изменения метаданных целиком относятся на Scheduler. Console служит только для управляющих операций (добавление и удаление Worker и т.п.).

### 1.1 Обязанности

- **Планирование архивации**: сканирование объектов ColdPending, агрегация в ArchiveBundle, планирование последовательной записи на ленту
- **Планирование восстановления**: управление очередью Restore, объединение запросов по archive/tape, планирование последовательного чтения ленты
- Объединение запросов на одну ленту / в один архивный комплект, меньше перестановок и позиционирования
- Управление параллелизмом, приоритетами и таймаутами для гарантии производительности и качества данных

### 1.2 Ограничения, связанные со свойствами ленты

| Свойство | Ограничение | Влияние на планирование |
|------|------|----------|
| последовательная запись | только последовательная запись, случайная невозможна | агрегация архивации должна давать один непрерывный поток записи |
| последовательное чтение | случайное чтение требует seek и дорого | объединение восстановлений упорядочивается по физическому расположению |
| стоимость перестановки ленты | загрузка/выгрузка манипулятором примерно 30s–2min | задачи на одну ленту объединяются в приоритетном порядке |
| размер блока | обычно 256KB–1MB, LTO поддерживает 64KB–8MB | выравнивание блоков архивации, согласование буфера |
| пропускная способность | LTO-9 примерно 400 MB/s, LTO-10 выше | потоковая запись, отказ от мелких IO |

## 2. Планировщик архивации: логика агрегации записи

### 2.1 Цели агрегации

- **Соответствие последовательной записи**: один ArchiveBundle соответствует одному непрерывному участку записи на ленте
- **Максимум пропускной способности**: агрегировать достаточно объектов, чтобы избежать мелких IO и полностью загрузить конвейер накопителя
- **Выравнивание по блоку**: согласование с block_size ленты (например, 256KB), меньше фрагментации внутреннего буфера накопителя

### 2.2 Стратегия формирования ArchiveBundle

#### 2.2.1 Измерения агрегации

| Измерение | Стратегия | Описание |
|------|------|------|
| **размер** | `min_archive_size_mb` ~ `max_archive_size_mb` | диапазон общего размера одного Bundle: слишком маленький — растрачивает перестановки ленты, слишком большой — одна задача идёт слишком долго |
| **число объектов** | `batch_size` | максимум объектов в Bundle, ограничивает издержки метаданных и индексов |
| **временное окно** | `aggregation_window_secs` | объекты ColdPending в одном окне могут быть агрегированы, без длительного ожидания |
| **корзина/префикс** | опционально агрегация в пределах bucket | удобно для дальнейшего управления по корзинам, не обязательно |

#### 2.2.2 Алгоритм агрегации (псевдокод)

```
1. просканировать объекты ColdPending, отсортировать по created_at или size
2. инициализировать текущий Bundle = []
3. для каждого объекта:
     если после добавления total_size <= max_archive_size_mb И count <= batch_size:
         Bundle.append(object)
     иначе:
         отправить текущий Bundle как ArchiveBundle
         сбросить Bundle, добавить в него объект
4. если остаток Bundle есть и total_size >= min_archive_size_mb: отправить
5. если остаток Bundle есть и total_size < min_archive_size_mb: ждать следующий раунд
   либо отправить принудительно по таймауту
```

#### 2.2.3 Физическое размещение на ленте

```
┌─────────────────────────────────────────────────────────────────┐
│  Физическое размещение на ленте (один ArchiveBundle)            │
├─────────────────────────────────────────────────────────────────┤
│ [FileMark] [Obj1 Header][Obj1 Data] [FileMark] [Obj2 Header]...   │
│     │           │           │          │                         │
│     │           │           │          └ границы объекта,       │
│     │           │           │            удобно позиционировать  │
│     │           │           └ непрерывная запись с выравниванием │
│     │           │              по блоку (256KB)                  │
│     │           └ метаданные: bucket, key, size, checksum, offset│
│     └ границы архивного комплекта, MTFSF/MTBSF позволяют пропускать│
└─────────────────────────────────────────────────────────────────┘
```

- **FileMark**: файловая метка MTIO, используется для позиционирования по «файлам» при seek
- **Блок объекта**: фиксированный или переменный блок, выровненный по `block_size`
- **Индекс**: логическое смещение каждого объекта внутри Bundle записывается в заголовок Bundle или в отдельную область индекса, чтобы использовать при позиционировании во время восстановления

### 2.3 Конвейер последовательной записи

```
┌──────────────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ чтение объекта   │───▶│ выравни- │───▶│ двойная  │───▶│ запись на│
│ (staging на      │    │ вание по │    │ буфери-  │    │ ленту    │
│  Cache Worker)   │    │ блоку    │    │ зация    │    │ (посл.)  │
└──────────────────┘    └──────────┘    └──────────┘    └──────────┘
```

- **Источник данных**: при архивации данные объекта читаются из staging на Cache Worker (`StagingReadApi.get_staging`), а не из внешней системы горячего хранения
- **Выравнивание по блоку**: хвост объекта меньше block_size дополняется (padding) либо используется переменный блок (нужна поддержка накопителя)
- **Двойная буферизация**: предварительное чтение следующей пачки данных при записи текущей, чтобы накопитель писал непрерывным потоком
- **Backpressure**: если чтение с Cache Worker медленнее записи на ленту, можно снизить параллелизм или увеличить буфер

### 2.4 Процесс архивации (детально)

1. **Слой планирования**: сканирует ColdPending в метаданных, получает `staging_id` и `staging_worker_id`
2. **Слой планирования**: агрегирует объекты в ArchiveBundle по стратегии
3. **Слой планирования**: выбирает целевую ленту (текущая точка записи или новая лента)
4. **Слой планирования → Cache Worker**: читает данные объектов из staging по `staging_id` (`StagingReadApi.get_staging`)
5. **Слой планирования → слой лент**: запрашивает ленточный накопитель, получает эксклюзивный доступ
6. **Слой лент**: последовательная запись: FileMark → [Obj1 Header + Data] → [Obj2...] → FileMark
7. **Слой планирования**: после завершения записи вычисляет и сохраняет контрольную сумму Bundle (опционально)
8. **Слой планирования → слой метаданных**: обновляет ObjectMetadata (Cold, archive_id, tape_id, tape_block_offset, очистка staging_id), ArchiveBundle, TapeInfo
9. **Слой планирования → Cache Worker**: удаляет staging-данные (`StagingWriteApi.delete_staging_batch`)
10. **Слой планирования → слой лент**: освобождает накопитель

> Источник данных на шаге 4 — staging на Cache Worker, а не внешнее hot-хранилище.
> Шаги 8-9 выполняет слой планирования; слой лент и слой кэша метаданные не пишут.

### 2.5 Ключевые параметры архивации

| Параметр | Рекомендуемое значение | Описание |
|------|--------|------|
| block_size | 262144 (256KB) | выравнивание по типичному блоку LTO |
| min_archive_size_mb | 100 | минимальный размер Bundle, чтобы не получался слишком мелким |
| max_archive_size_mb | 10240 (10GB) | максимальный размер Bundle, ограничивает длительность одной задачи |
| batch_size | 500–2000 | число объектов в Bundle |
| write_buffer_mb | 64–128 | буфер записи, согласование с конвейером накопителя |
| target_throughput_mbps | 300 | целевая пропускная способность; LTO-9 достигает 400 |

## 3. Планировщик восстановления: логика агрегации извлечения

### 3.1 Цели агрегации

- **Меньше перестановок ленты**: несколько запросов на одной ленте объединяются в одну загрузку и одно последовательное чтение
- **Меньше seek**: внутри одного archive сортировка по физическому смещению, последовательное чтение
- **Объединение запросов к одному объекту**: если один объект размораживают несколько раз, чтение выполняется один раз, результат рассылается нескольким заявителям

### 3.2 Стратегия объединения восстановлений

#### 3.2.1 Уровни объединения

```
Уровень 1: несколько объектов с одинаковым archive_id
           → одно чтение ленты, сортировка по tape_block_offset, последовательное чтение

Уровень 2: несколько archive на одной tape_id
           → одна перестановка ленты, сортировка по физическому порядку archive на ленте

Уровень 3: несколько RecallTask на один объект (повторные запросы)
           → объединяются в одно чтение, результат рассылается нескольким заявителям
```

#### 3.2.2 Алгоритм объединения (псевдокод)

```
1. достать из очереди набор RecallTask, ожидающих планирования
2. сгруппировать по tape_id
3. для каждой tape_id:
     tasks = все задачи на этой ленте
     отсортировать по (archive_id, tape_block_offset) для гарантии последовательного чтения
     при наличии нескольких задач с одинаковым (bucket, key) — дедуплицировать, оставить одно чтение
     сформировать TapeReadJob: { tape_id, [(archive_id, [objects])] }
4. отсортировать TapeReadJob по приоритету (Expedited > Standard > Bulk)
5. выдать свободные накопители, выполнить TapeReadJob
```

#### 3.2.3 Порядок чтения ленты

```
Физический порядок на ленте: Archive1 → Archive2 → Archive3 → ...

Запросы на восстановление: Obj_A∈Archive2, Obj_B∈Archive1, Obj_C∈Archive2

Оптимизированный порядок чтения:
  1. Seek к началу Archive1
  2. прочитать Obj_B
  3. Seek к началу Archive2 (или seek не нужен, если проходим последовательно)
  4. последовательно прочитать Obj_A, Obj_C
```

- объекты внутри одного Archive сортируются по `tape_block_offset`, чтобы читать их последовательно
- при переходе между Archive сами Archive выстраиваются в физическом порядке ленты, чтобы избежать движения назад (MTBSF дороже, чем MTFSF)

### 3.3 Процесс восстановления (детально)

1. **Протокольный слой → слой планирования**: приём запроса Restore; протокольный слой читает ObjectMetadata, получает `archive_id`, `tape_id`, `tape_block_offset`, `object_size`, `checksum` и другие, формирует RecallTask и передаёт его слою планирования для постановки в очередь
2. **Слой планирования**: берёт задачи из очереди, объединяет по tape_id + archive_id
3. **Слой планирования → слой лент**: проверка состояния ленты; ONLINE → продолжаем, OFFLINE → оповещение и ожидание
4. **Слой планирования → слой лент**: запрос накопителя, загрузка ленты (если не загружена)
5. **Слой лент**: чтение в физическом порядке: Seek → Read → возврат данных
6. **Слой планирования → слой кэша**: `cache.put_restored(bucket, key, data, checksum, expire_at)`
7. **Слой планирования → слой метаданных**: обновление restore_status=Completed, restore_expire_at
8. **Слой планирования → слой лент**: освобождение накопителя

> Шаги 6-7 отражают ключевой принцип варианта B: слой планирования сначала пишет кэш, затем обновляет метаданные. Ни слой кэша, ни слой лент MetadataClient не хранят.

### 3.4 Ключевые параметры восстановления

| Параметр | Рекомендуемое значение | Описание |
|------|--------|------|
| queue_size | 10000 | вместимость очереди |
| max_concurrent_restores | число накопителей | на каждый накопитель — свой конвейер восстановления |
| restore_timeout_secs | 3600 | таймаут одной задачи |
| min_restore_interval_secs | 300 | минимальный интервал восстановления (SLA 5 минут) |
| read_buffer_mb | 64 | буфер чтения |
| merge_window_secs | 60 | окно объединения: задачи на одну ленту внутри окна можно объединить |

## 4. Механизм планирования

### 4.1 Выдача накопителей и конкуренция

| Ресурс | Стратегия |
|------|------|
| ленточные накопители | архивация и восстановление делят общий пул накопителей, пропорция настраивается (например, 2:1 или отдельные пулы) |
| приоритет | восстановление Expedited > архивация > восстановление Standard > восстановление Bulk |
| вытеснение | как правило не вытесняем; после завершения текущей задачи накопитель выдаётся по приоритету |
| резервирование | для Expedited можно зарезервировать 1 накопитель, чтобы гарантировать высокий приоритет |

### 4.2 Модель очереди

```
                    ┌─────────────────────────────────┐
                    │     Приоритетная очередь Recall  │
                    │  Expedited | Standard | Bulk    │
                    └─────────────────────────────────┘
                                        │
                    ┌───────────────────┼───────────────────┐
                    ▼                   ▼                   ▼
            ┌───────────────┐   ┌───────────────┐   ┌───────────────┐
            │   объединение │   │   объединение │   │   объединение │
            │ (агрегация по │   │ (агрегация по │   │ (агрегация по │
            │     ленте)    │   │     ленте)    │   │     ленте)    │
            └───────┬───────┘   └───────┬───────┘   └───────┬───────┘
                    │                   │                   │
                    └───────────────────┼───────────────────┘
                                        ▼
                    ┌─────────────────────────────────┐
                    │     планировщик накопителей     │
                    │  Drive 1 | Drive 2 | Drive 3    │
                    └─────────────────────────────────┘
```

### 4.3 Цикл планирования архивации

- **Период сканирования**: `scan_interval_secs` (по умолчанию 60s)
- **Условия запуска**: по таймеру + опционально по событию (накопление ColdPending выше порога)
- **Параллелизм**: при нескольких накопителях несколько ArchiveTask выполняются параллельно, каждый Task эксклюзивно занимает один накопитель

## 5. Проектирование производительности

### 5.1 Цели по пропускной способности

| Сценарий | Цель | Ключевые моменты реализации |
|------|------|----------|
| запись при архивации | ≥ 300 MB/s | выравнивание по блоку, двойная буферизация, потоковая запись |
| восстановление | ≥ 1 задачи/5 минут | объединение сокращает перестановки, параллельная работа нескольких накопителей |

### 5.2 Оптимизация производительности

| Приём | Описание |
|------|------|
| выравнивание по блоку | блоки 256KB, меньше внутренней фрагментации накопителя |
| большие буферы | буферы записи/чтения 64–128MB |
| упреждающее чтение | при архивации заранее читается следующая пачка объектов |
| объединение | при восстановлении объединяются задачи на одну ленту и в один archive |
| параллелизм | при нескольких накопителях архивация и восстановление идут параллельно |

### 5.3 Backpressure и ограничение интенсивности

- Архивация: если чтение из hot-хранилища медленное, можно приостановить отправку новых Bundle
- Восстановление: при заполненной очереди новые Restore отклоняются с 503
- Expedited: настраивается максимум параллельных задач; при превышении возвращается GlacierExpeditedRetrievalNotAvailable

## 6. Качество и надёжность

### 6.1 Целостность данных

| Механизм | Описание |
|------|------|
| контрольная сумма объекта | при архивации записывается CRC32/SHA256, при восстановлении проверяется |
| контрольная сумма Bundle | опционально, проверка всего Bundle |
| проверка после записи | опционально, чтение обратно после завершения архивации (дорого) |

### 6.2 Отказы и повторы

| Сценарий | Стратегия |
|------|------|
| сбой записи при архивации | 3 повтора; при повторном отказе Bundle помечается Failed, объекты откатываются в ColdPending |
| сбой чтения при восстановлении | 2 повтора; при повторном отказе RecallTask помечается Failed, пользователь уведомляется |
| неисправность накопителя | переключение на резервный накопитель, повторная загрузка ленты |
| лента не читается | если есть реплика — переключение на реплику; иначе оповещение человека |

### 6.3 Согласованность (координация на уровне слоя планирования)

Слой планирования — единственный координатор записи метаданных и обязан соблюдать следующий порядок записи:

**Архивация**:

| Порядок | Операция | Обработка сбоя |
|------|------|----------|
| 1 | последовательная запись на ленту завершена | повтор / смена ленты |
| 2 | **слой планирования → слой метаданных**: обновление ObjectMetadata, ArchiveBundle, TapeInfo | повтор / задача компенсации |

**Восстановление**:

| Порядок | Операция | Обработка сбоя |
|------|------|----------|
| 1 | чтение с ленты завершено | повтор / переключение на реплику |
| 2 | **слой планирования → слой кэша**: put_restored | повтор / пометка Failed |
| 3 | **слой планирования → слой метаданных**: restore_status=Completed | повтор; при стабильном сбое в кэше данные есть, но GET недоступен — нужна компенсация |

> Слой кэша и слой лент — ведомые стороны, они инициативно метаданные не пишут.

## 7. Обработка офлайн-лент

- Состояния ленты: ONLINE / OFFLINE / UNKNOWN
- Если восстановление попало на ленту OFFLINE:
  1. формируется событие оповещения (tape_id, слот, archive_id, заявитель)
  2. задача переходит в очередь ожидания и не занимает накопитель
  3. после ручной загрузки ленты и подтверждения ONLINE планировщик автоматически повторяет попытку
- Объединение: если несколько запросов попали на одну офлайн-ленту, они объединяются в одно оповещение, а после загрузки обрабатываются пакетно

## 8. Обработка DeleteObject для заархивированных данных

### 8.1 Принцип проектирования

Лента — носитель с дополняющей записью, уже записанные данные нельзя удалить произвольно. Операцию DeleteObject нужно обрабатывать в две фазы:

1. **Немедленная фаза**: сразу удаляются метаданные и данные в кэше
2. **Отложенная фаза освобождения**: физическое место на ленте освобождается через «пометку удаления + уплотнение ленты»

### 8.2 Процесс DeleteObject

```
Обработка запроса DeleteObject:

1. Scheduler получает запрос DELETE, переданный Gateway
2. Scheduler → Metadata: чтение ObjectMetadata
3. Развилка по состоянию объекта:

   ── ColdPending (ещё не заархивирован):
   4a. Scheduler → Cache Worker: DeleteStaging(staging_id)  // удалить staging-данные
   5a. Scheduler → Metadata: DeleteObject                   // удалить метаданные
   6a. готово: staging-данные и метаданные очищены

   ── Cold (заархивирован на ленту):
   4b. Scheduler → Cache Worker: Delete(bucket, key)         // очистить кэш разморозки (если есть)
   5b. Scheduler → Metadata: MarkObjectDeleted(bucket, key)  // пометить метаданные как Deleted
       └─ ObjectMetadata сразу не удаляется: archive_id/tape_id сохраняются
          как ориентир для последующего уплотнения ленты
   6b. Scheduler → Metadata: IncrementBundleDeleteCount(archive_id)
       └─ фиксируется число удалённых объектов в ArchiveBundle
   7b. готово: физические данные на ленте освобождаются при последующем уплотнении
```

### 8.3 Стратегия освобождения места на ленте

Место на ленте на месте не освобождается; это делается через **уплотнение ленты (Tape Compaction)**.
Когда доля полезных данных на ленте падает ниже порога, запускается уплотнение:

| Параметр | Рекомендуемое значение | Описание |
|------|--------|------|
| `compaction_threshold` | 0.3 | уплотнение запускается, когда полезных данных меньше 30% |
| `compaction_scan_interval_secs` | 86400 | сканирование раз в сутки |

**Процесс уплотнения**:

```
1. сканировать TapeInfo и вычислить долю полезных данных каждой ленты:
   доля полезного = (всего записано - размер удалённых объектов) / общая ёмкость
2. для лент с долей полезного < compaction_threshold:
   a. прочитать все неудалённые объекты с ленты
   b. агрегировать полезные объекты в новые ArchiveBundle
   c. записать на новую ленту
   d. обновить метаданные (новые archive_id, tape_id)
   e. старую ленту пометить как пригодную для повторного использования или на вывод из эксплуатации
```

### 8.4 Расширение состояния ObjectMetadata

Чтобы поддержать отложенное удаление, в `StorageClass` новые состояния не нужны. DeleteObject удаляет запись прямо из `cf_objects`,
но в `cf_deleted_objects` сохраняет необходимую информацию как ориентир для уплотнения ленты:

```rust
pub struct DeletedObjectRecord {
    pub bucket: String,
    pub key: String,
    pub archive_id: Uuid,
    pub tape_id: String,
    pub size: u64,
    pub deleted_at: DateTime<Utc>,
}
```

Соответствующая новая Column Family:

| Имя CF | Формат Key | Тип Value | Описание |
|---------|----------|-----------|------|
| `cf_deleted_objects` | `del:{archive_id}:{bucket}:{key}` | DeletedObjectRecord | записи об удалённых объектах, ориентир для уплотнения ленты |

### 9.5 ObjectHeader (заголовок объекта на ленте)

При записи на ленту перед каждым объектом пишется Header в смешанном формате **фиксированный префикс + переменная длина bucket/key**. При разборе сначала читается фиксированная часть, извлекаются `bucket_len`/`key_len`, затем строки переменной длины читаются по этим длинам.

> ObjectHeader и BundleEntry частично дублируют друг друга: BundleEntry хранит те же сведения в метаданных. Назначение ObjectHeader — **самонастраиваемость на стороне ленты**: определение границ (magic), проверка при восстановлении (checksum) и восстановление данных при утрате метаданных.

```rust
pub struct ObjectHeader {
    pub magic: [u8; 4],
    pub version: u8,
    pub bucket_len: u16,
    pub bucket: String,
    pub key_len: u16,
    pub key: String,
    pub size: u64,
    pub checksum: [u8; 32],
    pub flags: u8,
    pub reserved: [u8; 16],
}
```

| Поле | Тип | Значение | Применение |
|------|------|------|------|
| `magic` | [u8; 4] | магическое число `0x43 0x53 0x4F 0x48` ("CSOH") | отмечает начало Header, проверка корректности формата |
| `version` | u8 | версия формата Header | обратная совместимость, сейчас `1` |
| `bucket_len` | u16 | длина строки bucket в байтах | позиционирование при разборе |
| `bucket` | String | имя корзины S3 | при восстановлении восстанавливается принадлежность объекта |
| `key_len` | u16 | длина строки key в байтах | позиционирование при разборе |
| `key` | String | ключ объекта S3 | при восстановлении восстанавливается идентификатор объекта |
| `size` | u64 | число байт данных объекта | при восстановлении читается точная длина |
| `checksum` | [u8; 32] | исходные байты SHA256 | побайтовая проверка при восстановлении |
| `flags` | u8 | флаги (bit 0: сжатие, bit 1: шифрование) | зарезервировано, сейчас все 0 |
| `reserved` | [u8; 16] | зарезервированные поля | на будущее, при записи все 0 |

| `bucket` | String | имя корзины S3 | передаётся при записи в кэш |
| `key` | String | ключ объекта S3 | передаётся при записи в кэш |
| `tape_block_offset` | u64 | блочное смещение на ленте | точное позиционирование `MTFSR(offset)` |
| `size` | u64 | размер объекта в байтах | выделение буфера чтения |
| `checksum` | String | SHA256 в hex | проверка после чтения |
| `expire_at` | DateTime\<Utc\> | срок истечения разморозки | запись в xattr кэша |

### 9.13 RecallQueue (приоритетная очередь восстановления)

```rust
pub struct RecallQueue {
    expedited: VecDeque<RecallTask>,
    standard: VecDeque<RecallTask>,
    bulk: VecDeque<RecallTask>,
    pending_by_tape: HashMap<String, Vec<Uuid>>,
    capacity: usize,
}
```

| Поле | Тип | Значение | Применение |
|------|------|------|------|
| `expedited` | VecDeque\<RecallTask\> | очередь срочных | наивысший приоритет, извлекается первым |
| `standard` | VecDeque\<RecallTask\> | очередь стандартных | средний приоритет |
| `bulk` | VecDeque\<RecallTask\> | очередь пакетных | наименьший приоритет |
| `pending_by_tape` | HashMap\<String, Vec\<Uuid\>\> | tape_id → список task_id в ожидании | при объединении быстро группировать по ленте |
| `capacity` | usize | предел общей вместимости очереди | при превышении новые задачи отклоняются |

**Правила поддержки pending_by_tape**:
- **постановка в очередь**: task_id добавляется в `pending_by_tape[tape_id]`
- **извлечение/объединение**: при объединении задачи извлекаются из `pending_by_tape` с группировкой по ленте и упорядочиваются вместе с приоритетной очередью
- **завершение/отмена**: после завершения или отмены задачи соответствующий task_id удаляется из `pending_by_tape`

## 12. Зависимости

**Активные зависимости слоя планирования**:

| Зависимость | Направление | Протокол | Описание |
|------|------|------|------|
| слой метаданных | Scheduler → Metadata | gRPC | **единственная бизнес-точка чтения и записи метаданных** |
| слой кэша | Scheduler → Cache Worker | gRPC (та же машина) | временное хранение/чтение данных |
| слой лент | Scheduler → Tape Worker | gRPC (удалённо) | выдача команд чтения и записи ленты |

**Кто зависит от слоя планирования**:

| Зависимая сторона | Протокол | Описание |
|----------|------|------|
| Gateway | gRPC | **все** S3-запросы (PUT/GET/HEAD/DELETE/Restore/List) |

> **Ключевой момент архитектуры**: Scheduler Worker — единственный бизнес-хаб; он одновременно хранит три зависимости: MetadataClient,
> CacheClient (gRPC) и TapeClient (gRPC).
> Все запросы Gateway идут в Scheduler; Gateway не подключается к Metadata/Cache/Tape напрямую.
> Слой кэша и слой лент — чистые функциональные компоненты, о метаданных они ничего не знают.

## 13. Ключевые моменты внедрения

- Архивация и восстановление масштабируются независимо
- Каждому ленточному накопителю соответствует один конвейер последовательного I/O; несколько задач не должны делить один накопитель, иначе растут seek
- Добавление накопителей линейно увеличивает параллельную ёмкость архивации и восстановления
- В метаданных нужно хранить `tape_block_offset`, чтобы при восстановлении сортировать по физическому порядку
- **В слой планирования одновременно внедряются MetadataClient + CacheWriteApi + StagingReadApi + TapeManager**; это единственный оркестратор в системе

## 14. Расширение на несколько Scheduler Worker (проектируется)

> **Статус: раздел-заглушка, конкретное решение будет определено позже.**

На текущем этапе Scheduler Worker работает в одном экземпляре; в дальнейшем нужна горизонтальная масштабируемость на несколько Scheduler Worker.
Ниже перечислены ключевые вопросы, которые следует решить в последующем проектировании:

### 14.1 Задачи, которые предстоит решить

| Вопрос | Описание | Возможные направления |
|------|------|----------|
| **сегментация сканирования ColdPending** | несколько Scheduler, сканирующих ColdPending одновременно, приведут к повторной архивации | разбиение по hash bucket/key, поддержка механизма claim на стороне Metadata |
| **распределение RecallTask** | как несколько Scheduler распределяют задачи восстановления | распределение с аффинностью к tape_id, распределённая блокировка через Metadata |
| **конкуренция за накопители** | несколько Scheduler конкурируют за накопители одного Tape Worker | очередь на стороне Tape Worker, договорённости между Scheduler |
| **основной/резервный vs одноранговые** | выбрать основной/резервный режим или одноранговый | основной/резервный проще, но переключение медленное; одноранговый требует более сложной координации |
| **переключение при отказе** | как перераспределить задачи при отказе Scheduler | задачи InProgress после таймаута подхватываются другим Scheduler |
| **аффинность к Cache Worker** | каждый Scheduler привязан к Cache Worker на той же машине | сохранять аффинность через `paired_cache_worker_id` |

### 14.2 Уже предусмотренные точки расширения интерфейса

В `SchedulerWorkerInfo` уже зарезервированы поля поддержки нескольких Scheduler:

- `is_active: bool` — в режиме основной/резервный отмечает активный Scheduler
- `paired_cache_worker_id: u64` — привязка к Cache Worker на той же машине

### 14.3 Ограничения

- Решение с несколькими Scheduler не должно менять существующий протокол gRPC-интерфейсов
- Gateway может настраивать несколько адресов Scheduler с поддержкой балансировки нагрузки
- Слою лент и слою кэша не нужно знать об изменении числа Scheduler

## 15. Точное определение использования FileMark

### 15.1 Физическая структура ArchiveBundle на ленте

Каждый ArchiveBundle размещается на ленте следующим образом. **FileMark пишется только на границах Bundle**,
между объектами внутри Bundle FileMark не пишется, позиционирование идёт по блочному смещению:

```
Физическое размещение на ленте:

[BOT] ... [FM_prev] [начало Bundle N] [Obj1 Header][Obj1 Data][Obj2 Header][Obj2 Data]...[ObjN Data] [FM_end] ...

Пояснение:
  - FM_prev:   завершающий FileMark предыдущего Bundle (он же точка позиционирования начала текущего Bundle)
  - данные Bundle: объекты пишутся подряд, без разделителей FileMark
  - FM_end:    FileMark, добавляемый после завершения записи текущего Bundle

Для первого Bundle:
  [BOT] [Obj1 Header][Obj1 Data]...[ObjN Data] [FM_0]

Для последующих Bundle:
  [FM_0] [Obj1 Header][Obj1 Data]...[ObjN Data] [FM_1]
```

### 15.2 Значение filemark_start и filemark_end

| Поле | Значение | Способ позиционирования при восстановлении |
|------|------|-------------|
| `filemark_start` | номер FileMark перед началом Bundle (сколько FM от BOT) | выполнить из BOT `MTFSF(filemark_start)`, чтобы перейти к началу Bundle |
| `filemark_end` | номер FileMark, записанного после конца Bundle | отмечает границы Bundle; у следующего Bundle `filemark_start = текущий filemark_end` |

Для первого Bundle на ленте `filemark_start = 0` (означает «начинать от BOT, пропускать FM не нужно»).

### 15.3 Позиционирование объекта внутри Bundle

Объекты внутри Bundle позиционируются по `tape_block_offset` (блочное смещение относительно начала Bundle):

```
Восстановление одного объекта:
1. MTFSF(filemark_start)    → переход к началу Bundle
2. MTFSR(tape_block_offset) → движение внутри Bundle по блочному смещению к целевому объекту
3. read(object_size)        → чтение данных объекта
```
