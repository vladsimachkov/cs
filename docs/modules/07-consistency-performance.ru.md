# Проектирование межслоевой согласованности данных и производительности

> Архитектура: система холодного хранения ColdStore  
> См. также: [Проектирование общей архитектуры](../DESIGN.ru.md) | [03 — кластер метаданных](./03-metadata-cluster.ru.md) | [04 — слой кэша](./04-cache-layer.ru.md) | [05 — слой планирования](./05-scheduler-layer.ru.md) | [06 — слой лент](./06-tape-layer.ru.md)

## 1. Контекст проектирования

ColdStore охватывает четыре ключевых слоя (метаданные → кэш → планирование → лента); каждая операция архивации или восстановления состоит из нескольких шагов записи, а целевой носитель (лента) отличается высокой задержкой и невозможностью случайной записи. Без поддержки распределённых транзакций окончательная согласованность достигается через **паттерн Saga + идемпотентные операции + механизм компенсации**, а целевая пропускная способность — через **конвейеры, агрегацию и управление параллелизмом**.

### 1.1 Ключевые ограничения

| Ограничение | Источник | Влияние |
|------|------|------|
| ленту нельзя откатить | лента пишется дополнением, отмена невозможна | архивная запись обязана идти «сначала лента, потом метаданные», порядок менять нельзя |
| последовательная запись в Raft | все записи упорядочиваются через Leader | запись метаданных — общее узкое место, нужна пакетная обработка |
| SPDK в пользовательском пространстве | слой кэша работает в отдельном потоке | межпоточное общение через channel/Arc, прямое разделение блокировок невозможно |
| задержка перестановки ленты | 30s–2min механических операций | слой планирования обязан объединять запросы на одну ленту, чтобы реже переставлять её |

### 1.2 Уровни согласованности

| Слой | Гарантия согласованности | Описание |
|------|-----------|------|
| кластер метаданных (03) | **строгая согласованность (линейная)** | консенсус Raft, запись подтверждается большинством |
| слой планирования (05) | **окончательная согласованность Saga** | многошаговые операции приходят к корректному итоговому состоянию за счёт компенсации |
| слой кэша (04) | **слабая согласованность (окончательная)** | данные кэша — «проекция» метаданных, могут теряться и пересоздаваться |
| слой лент (06) | **согласованность персистентности** | после успешной записи данные устойчивы, гарантируется двумя репликами |

## 2. Модель согласованности данных

### 2.1 Строгая согласованность метаданных (консенсус Raft)

```
                путь записи
Client ──▶ Leader ──▶ Propose в Raft
                        │
              ┌─────────┼─────────┐
              ▼         ▼         ▼
          Follower1  Follower2  Leader
              │         │         │
              └────┬────┘         │
            Ack от большинства   │
                   └──────▶ Commit ──▶ Apply ──▶ RocksDB
```

**Ключевые гарантии**:

| Гарантия | Реализация | Применяется в |
|------|------|----------|
| атомарность записи | один `ColdStoreRequest` — одна запись журнала Raft | все операции записи |
| порядок записи | индекс журнала Raft глобально упорядочен | переходы состояний одного объекта не перепутываются |
| линейное чтение | `ensure_linearizable()` подтверждает роль Leader | `find_active_recall` при обнаружении дублей |
| окончательная согласованность чтения | локальное RocksDB на любом узле | GET читает restore_status |

**Оптимизация объединения записей**:

Для операций вроде завершения архивации, которые одновременно обновляют несколько CF, внутри apply конечного автомата используется RocksDB `WriteBatch`, обеспечивающий атомарность:

```rust
fn apply_archive_complete(
    &self,
    bundle: &ArchiveBundle,
    object_updates: &[(String, String, Uuid, String, Vec<String>, u64)],
) -> Result<()> {
    let mut batch = WriteBatch::default();

    // 1. запись ArchiveBundle
    batch.put_cf(cf_bundles, bundle_key, serialize(bundle));

    // 2. пакетное обновление ObjectMetadata
    for (bucket, key, archive_id, tape_id, tape_set, offset) in object_updates {
        let obj_key = format!("obj:{}:{}", bucket, key);
        let mut meta: ObjectMetadata = self.get_cf(cf_objects, &obj_key)?;
        meta.storage_class = StorageClass::Cold;
        meta.archive_id = Some(*archive_id);
        meta.tape_id = Some(tape_id.clone());
        meta.tape_set = Some(tape_set.clone());
        meta.tape_block_offset = Some(*offset);
        meta.updated_at = Utc::now();
        batch.put_cf(cf_objects, &obj_key, serialize(&meta));

        // 3. удаление индекса ColdPending
        let pend_key = format!("pend:{}:{}:{}", meta.created_at.timestamp(), bucket, key);
        batch.delete_cf(cf_idx_pending, &pend_key);

        // 4. запись обратного индекса
        let ibo_key = format!("ibo:{}:{}:{}", archive_id, bucket, key);
        batch.put_cf(cf_idx_bundle_objects, &ibo_key, b"");
    }

    // 5. запись индекса «лента → Bundle»
    let itb_key = format!("itb:{}:{}", bundle.tape_id, bundle.id);
    batch.put_cf(cf_idx_tape_bundles, &itb_key, b"");

    self.db.write(batch)?;
    Ok(())
}
```

### 2.2 Согласованность процесса архивации (паттерн Saga)

Архивация — необратимая операция (данные на ленте уже записаны), поэтому применяется стратегия **восстановления вперёд**:

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                        Saga-процесс архивации                                │
│                                                                              │
│  Шаг 1           Шаг 2              Шаг 3              Шаг 4                 │
│  скан и   ──▶   выдача накопителя ──▶ последовательная ──▶ обновление       │
│  агрегация      /ленты               запись на ленту     метаданных         │
│  (слой          (слой лент)          (слой лент)         (слой метаданных)  │
│   планирования)                                                              │
│                                                                              │
│  Обработка отказов:                                                          │
│  сбой шага 1: побочных эффектов нет, прямой повтор                          │
│  сбой шага 2: освободить ресурсы, повторная постановка в очередь            │
│  сбой шага 3: ┌─ повтор (та же лента / другая лента)                        │
│               └─ лимит исчерпан → Bundle помечается Failed, объект           │
│                  откатывается в ColdPending                                 │
│  сбой шага 4: ┌─ лента уже записана (откат невозможен)                      │
│               ├─ повтор обновления метаданных (экспоненциальная задержка,    │
│               │  максимум 10 раз)                                            │
│               └─ лимит исчерпан → запись в журнал компенсации, фоновая       │
│                  задача восстановления периодически сканирует и повторяет     │
└──────────────────────────────────────────────────────────────────────────────┘
```

**Ключевые инварианты**:

| Инвариант | Значение | Последствия нарушения | Механизм защиты |
|--------|------|----------|----------|
| запись на ленту → обновление метаданных | сначала подтверждается персистентность на ленте, затем отметка Cold | при обратном порядке: в метаданных Cold, а на ленте данных нет, при восстановлении данные теряются | принудительный порядок + повтор шага 4 |
| уникальность archive_id | каждый Bundle глобально уникален | при дубле: сведения старого Bundle перезаписываются | UUID v4 + идемпотентная запись |
| атомарность ColdPending → Cold | переход состояния нельзя пропустить | при пропуске: некорректное состояние объекта | атомарная операция WriteBatch |

**Журнал компенсации**:

Если шаг 4 стабильно завершается ошибкой, незавершённое обновление метаданных записывается в локальный журнал компенсации:

```rust
pub struct CompensationEntry {
    pub id: Uuid,
    pub created_at: DateTime<Utc>,
    pub saga_type: SagaType,
    pub payload: CompensationPayload,
    pub retry_count: u32,
    pub last_retry_at: Option<DateTime<Utc>>,
    pub status: CompensationStatus,
}

pub enum SagaType {
    ArchiveComplete,
    RecallComplete,
}

pub enum CompensationPayload {
    ArchiveComplete {
        bundle: ArchiveBundle,
        object_keys: Vec<(String, String)>,
    },
    RecallComplete {
        recall_task_id: Uuid,
        bucket: String,
        key: String,
        restore_expire_at: DateTime<Utc>,
    },
}

pub enum CompensationStatus {
    Pending,
    Retrying,
    Resolved,
    Abandoned,
}
```

**Планировщик задачи компенсации**:

```rust
pub struct CompensationRunner {
    metadata: Arc<MetadataClient>,
    log_store: Arc<CompensationLogStore>,
    config: CompensationConfig,
}

pub struct CompensationConfig {
    pub scan_interval_secs: u64,       // интервал сканирования: 60s
    pub max_retries: u32,              // максимум повторов: 100
    pub retry_backoff_base_ms: u64,    // база задержки: 1000ms
    pub retry_backoff_max_ms: u64,     // предел задержки: 300_000ms (5 минут)
    pub abandon_after_hours: u64,      // отказ по таймауту: 72 часа
}
```

### 2.3 Согласованность процесса восстановления (паттерн Saga)

Процесс восстановления затрагивает три цели (лента → кэш → метаданные) и использует **восстановление вперёд + отказ с деградацией**:

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                     Saga-процесс восстановления                              │
│                                                                              │
│  Шаг 1           Шаг 2             Шаг 3             Шаг 4                   │
│  выдача    ──▶  чтение     ──▶  запись в     ──▶  обновление                │
│  накопителя,    ленты            кэш                метаданных               │
│  позиционирование (слой лент)  (слой кэша)      (слой метаданных)           │
│  ленты (слой лент)                                                             │
│                                                                              │
│  Обработка отказов:                                                          │
│  сбой шага 1: освободить ресурсы, повторная постановка в очередь /          │
│               WaitingForMedia (офлайн)                                      │
│  сбой шага 2: ┌─ повтор (та же лента, 2 раза)                               │
│               ├─ переключение на ленту-реплику (следующая в tape_set)       │
│               └─ лимит исчерпан → RecallTask Failed                         │
│  сбой шага 3: ┌─ запустить вытеснение кэша и повторить (2 раза)             │
│               └─ лимит исчерпан → RecallTask Failed, метаданные не обновляются│
│  сбой шага 4: ┌─ в кэше уже есть данные (откат невозможен, ожидание         │
│               │  автоматической очистки по TTL)                              │
│               ├─ повтор обновления метаданных (экспоненциальная задержка,    │
│               │  максимум 10 раз)                                            │
│               └─ лимит исчерпан → запись в журнал компенсации; при этом      │
│                  данные в кэше есть, но GET недоступен                       │
└──────────────────────────────────────────────────────────────────────────────┘
```

**Конечный автомат восстановления**:

```
                        ┌─────────────────────────────────┐
                        │                                 │
                        ▼                                 │
  RestoreObject ──▶ Pending ──▶ WaitingForMedia ──────────┘
                        │              (после выхода офлайн-ленты в онлайн)
                        ▼
                   InProgress ──▶ Completed
                        │              │
                        ▼              └──▶ Expired (истёк TTL)
                      Failed
```

| Переход состояния | Условие запуска | Кто пишет | Идемпотентность |
|----------|----------|--------|--------|
| → Pending | API RestoreObject | протокольный слой | линейное чтение `find_active_recall` против дублей |
| Pending → WaitingForMedia | лента Offline | слой планирования | идемпотентно: повторная установка без побочных эффектов |
| WaitingForMedia → Pending | подтверждено Online ленты | слой планирования | идемпотентно |
| Pending → InProgress | выдан накопитель, началось чтение | слой планирования | идемпотентно |
| InProgress → Completed | запись в кэш и обновление метаданных успешны | слой планирования | идемпотентно: повторная запись того же значения |
| InProgress → Failed | превышен максимум повторов | слой планирования | идемпотентно |
| Completed → Expired | expire_at < now | фоновый скан | идемпотентно |

### 2.4 Согласованность «кэш — метаданные»

Слой кэша не хранит MetadataClient (вариант B), поэтому между данными кэша и метаданными существует естественное окно слабой согласованности:

| Сценарий | Состояние кэша | Состояние метаданных | Что видит пользователь | Способ самолечения |
|------|----------|-----------|-------------|----------|
| штатное восстановление завершено | данные есть | Completed | GET нормально возвращает данные | — |
| шаг 3 успешен, шаг 4 ждёт повтора | данные есть | InProgress/Pending | GET возвращает 403 (не разморожено) | задача компенсации повторяет обновление метаданных |
| вытеснение из кэша (TTL/ёмкость) | данных нет | Completed | GET возвращает 503 | пользователь повторно вызывает RestoreObject |
| кэш повреждён | проверка данных не пройдена | Completed | GET возвращает 500 | удалить повреждённый Blob, пользователь повторно Restore |
| в метаданных Expired, а из кэша не вытеснено | данные есть | Expired | GET возвращает 403 | скан TTL в кэше в итоге удалит данные |

**Принцип проектирования**: метаданные — **единственный источник истины** (Source of Truth), кэш лишь слой оптимизации производительности. Любая потеря кэша восстанавливается повторным RestoreObject.

### 2.5 Проектирование идемпотентности

Все межслоевые операции обязаны быть идемпотентными, чтобы повторы были безопасны:

| Операция | Ключ идемпотентности | Реализация идемпотентности |
|------|----------|----------|
| PutObject | `(bucket, key)` | запись с перезаписью: повторный PUT с тем же key перезаписывает прежнее значение |
| PutArchiveBundle | `bundle.id` (Uuid) | повторная запись с тем же id перезаписывает; CF `bundles` дедуплицируется по id |
| UpdateStorageClass | `(bucket, key, class)` | повторная установка того же значения без побочных эффектов |
| UpdateArchiveLocation | `(bucket, key)` | повторная установка того же значения без побочных эффектов |
| UpdateRestoreStatus | `(bucket, key, status)` | проверка конечного автомата: разрешены только корректные переходы |
| PutRecallTask | `recall.id` (Uuid) | повторная запись с тем же id перезаписывает |
| put_restored (кэш) | `(bucket, key)` | повторная запись с тем же key перезаписывает старый Blob |

**Защита конечного автомата**:

```rust
fn validate_restore_transition(current: &RestoreStatus, target: &RestoreStatus) -> bool {
    matches!(
        (current, target),
        (RestoreStatus::Pending, RestoreStatus::InProgress)
        | (RestoreStatus::Pending, RestoreStatus::WaitingForMedia)
        | (RestoreStatus::Pending, RestoreStatus::Failed)
        | (RestoreStatus::WaitingForMedia, RestoreStatus::Pending)
        | (RestoreStatus::WaitingForMedia, RestoreStatus::Failed)
        | (RestoreStatus::InProgress, RestoreStatus::Completed)
        | (RestoreStatus::InProgress, RestoreStatus::Failed)
        | (RestoreStatus::Completed, RestoreStatus::Expired)
    )
}
```

## 3. Модель управления параллелизмом

### 3.1 Общая архитектура параллелизма

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                              Tokio Runtime                                    │
│                                                                              │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐   │
│  │ S3 Handler   │  │ Archive      │  │ Recall       │  │ Compensation │   │
│  │ (параллельные│  │ Scheduler    │  │ Scheduler    │  │ Runner       │   │
│  │  запросы)    │  │ (один цикл)  │  │ (один цикл)  │  │ (один цикл)  │   │
│  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘   │
│         │                 │                 │                 │             │
│         ▼                 ▼                 ▼                 ▼             │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │                    Arc<MetadataClient>                                │  │
│  │  внутри: Raft client (автоматическая переадресация на Leader)         │  │
│  │  потоковая безопасность: журнал Raft сериализует все записи           │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                              │
│  ┌──────────────────────────┐  ┌───────────────────────────────────────┐   │
│  │ Arc<CacheManager>       │  │ Arc<TapeManager>                      │   │
│  │ внутри: RwLock<CacheIndex│ │ внутри: Mutex<DriveAllocator>         │   │
│  │ + пул потоков SPDK      │  │ + последовательный executor на накопитель│ │
│  └──────────────────────────┘  └───────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 Стратегия блокировок и гранулярность

| Компонент | Тип блокировки | Гранулярность | Время удержания | Сценарий конкуренции |
|------|--------|------|----------|----------|
| MetadataClient | **без блокировок** (сериализация через Raft) | глобально | N/A | все записи упорядочиваются Leader Raft, блокировки на уровне приложения не нужны |
| CacheIndex | `RwLock` | глобальный индекс | микросекунды (операции HashMap в памяти) | блокировка на чтение в горячем пути GET + блокировка на запись в put_restored |
| CacheBackend (SPDK) | **без блокировок** (модель потоков reactor SPDK) | per-thread | N/A | потоковую безопасность гарантирует сам SPDK |
| DriveAllocator.available | `Mutex` | пул накопителей | микросекунды | архивация и восстановление одновременно просят накопитель |
| DriveAllocator.waiters | `Mutex` | очередь ожидания | микросекунды | пробуждение ожидающих при возврате накопителя |
| CacheStats | `AtomicU64` | на счётчик | наносекунды | частое обновление статистики |
| RecallQueue | `Mutex` | на очередь | микросекунды | постановка/извлечение/объединение |

### 3.3 Анализ ключевых параллельных путей

#### 3.3.1 Горячий путь GET (самый частый)

```
GET /{bucket}/{key}
    │
    ├─ 1. metadata.get_object()          ← локальное чтение на Follower, без блокировок, < 100μs
    │
    ├─ 2. проверка storage_class/restore_status ← чистое решение в памяти
    │
    └─ 3. cache.get(bucket, key)
              │
              ├─ 3a. index.read()          ← блокировка на чтение RwLock, < 1μs
              │
              └─ 3b. backend.read_blob()   ← асинхронный I/O SPDK, 10-100μs (NVMe)
```

**Оптимизация**: на пути GET блокировок на запись нет вовсе, издержки блокировки на чтение пренебрежимо малы. Метаданные читаются локально на Follower (окончательная согласованность), небольшая задержка допустима.

#### 3.3.2 Путь записи put_restored

```
put_restored(item)
    │
    ├─ 1. backend.create_blob(xattrs, size)   ← создание Blob в SPDK, асинхронно
    │
    ├─ 2. backend.write_blob(blob_id, data)   ← запись данных в SPDK, асинхронно
    │
    └─ 3. index.write()                        ← блокировка на запись RwLock, < 1μs
```

**Оптимизация**: блокировка на запись удерживается только на последнем шаге при обновлении индекса в памяти, время удержания крайне мало. I/O SPDK выполняется без блокировки CacheIndex.

#### 3.3.3 Конкуренция за выдачу накопителей

```
acquire_drive(priority)
    │
    ├─ 1. lock(available)                ← Mutex, < 1μs
    │     ├─ есть свободный накопитель: pop + return DriveGuard
    │     └─ свободных нет:
    │           lock(waiters)            ← Mutex, < 1μs
    │           push(DriveWaiter { priority, oneshot })
    │           drop(available)
    │           await oneshot.recv()     ← ожидание освобождения накопителя, возможно несколько минут
    │
    └─ Drop у DriveGuard:
          lock(available)
          if waiters.peek().priority ≤ current:
              pop waiter, send drive via oneshot
          else:
              push drive back to available
```

**Оптимизация**: Mutex защищает только операции с структурами данных в памяти (микросекунды), фактическое ожидание асинхронизировано через `oneshot channel` и не блокирует потоки Tokio.

### 3.4 Предотвращение взаимных блокировок

| Правило | Описание |
|------|------|
| упорядочивание блокировок | если нужно удерживать несколько блокировок одновременно, они берутся в фиксированном порядке: `CacheIndex` → `DriveAllocator` |
| отсутствие вложенных блокировок | у MetadataClient нет блокировок уровня приложения, внутренние блокировки SPDK наружу не публикуются |
| Mutex + async | все `Mutex` освобождаются до `await`; `tokio::sync::Mutex` используется только там, где блокировка обязана пересекать await |
| защита таймаутом | `acquire_drive` имеет таймаут (`drive_acquire_timeout_secs`), исключающий бесконечное ожидание |

### 4.1 Целевые сквозные показатели

| Сценарий | Цель | Узкое место | Ключевая оптимизация |

### 4.2 Производительность слоя метаданных (03)

#### 4.2.1 Пакетная запись

В сценариях частой записи (например, массовое обновление ObjectMetadata при завершении архивации) составные команды сокращают число обменов с Raft:

```rust
pub enum ColdStoreRequest {
    // операции с одним объектом (низкая частота)
    PutObject(ObjectMetadata),

    // пакетные операции (высокая частота, обновление нескольких CF одной записью журнала Raft)
    BatchArchiveComplete {
        bundle: ArchiveBundle,
        tape_info_update: TapeInfo,
        object_updates: Vec<ObjectArchiveUpdate>,
    },
    BatchRecallComplete {
        task_updates: Vec<RecallTaskUpdate>,
        object_updates: Vec<ObjectRestoreUpdate>,
    },
}

pub struct ObjectArchiveUpdate {
    pub bucket: String,
    pub key: String,
    pub archive_id: Uuid,
    pub tape_id: String,
    pub tape_set: Vec<String>,
    pub tape_block_offset: u64,
}

pub struct ObjectRestoreUpdate {
    pub bucket: String,
    pub key: String,
    pub status: RestoreStatus,
    pub expire_at: Option<DateTime<Utc>>,
}

pub struct RecallTaskUpdate {
    pub id: Uuid,
    pub status: RestoreStatus,
    pub completed_at: Option<DateTime<Utc>>,
    pub error: Option<String>,
}
```

**Выгода**: для одного ArchiveBundle (500 объектов) нужна 1 запись журнала Raft вместо 500+1.

#### 4.2.2 Оптимизация пути чтения

| Оптимизация | Реализация | Выгода |
|------|------|------|
| чтение на Follower | GET/HEAD читают локальное RocksDB напрямую | чтение горизонтально масштабируется, минуя Leader |
| сканирование по префиксу | `cf_idx_pending` с ключами, упорядоченными по времени | `scan_cold_pending` не требует полного обхода таблицы |
| изоляция Column Family | 12 независимых CF | чтение и запись не мешают друг другу, компакция независима |
| Block Cache | настройка block_cache в RocksDB | метаданные горячих объектов кэшируются в памяти |
| Bloom Filter | Bloom Filter настроен на каждом CF | меньше дискового I/O по несуществующим ключам |

### 4.3 Производительность слоя кэша (04)

#### 4.3.1 Преимущества I/O SPDK в пользовательском пространстве

```
            традиционный путь ядра              пользовательский путь SPDK
App ──▶ syscall ──▶ VFS ──▶ Block Layer      App ──▶ SPDK Blobstore ──▶ NVMe Driver
         │          │           │                         │
   переключение    конкуренция  обработка              опрос (polling)
   контекста       блокировок   прерываний
   ~2μs            ~1μs         ~5μs                   < 1μs
```

| Показатель | Путь ядра | Путь SPDK | Улучшение |
|------|---------|-----------|------|
| задержка случайного чтения 4KB | 10-20μs | 2-5μs | 3-5x |
| задержка случайной записи 4KB | 15-30μs | 3-8μs | 3-5x |
| IOPS (случайное чтение 4KB) | 200-400K | 800K-1.5M | 3-4x |
| CPU на IOPS | высокий (прерывания + переключение контекста) | низкий (опрос) | заметное снижение |

#### 4.3.2 Конвейер чтения и записи кэша

```
Конвейер записи (пакет put_restored):

  Object A ──▶ [create_blob] ──▶ [write_data] ──▶ [update_index]
  Object B ──▶ [create_blob] ──▶ [write_data] ──▶ [update_index]
  Object C ──▶ [create_blob] ──▶ [write_data] ──▶ [update_index]
              ↑                                    ↑
   асинхронный параллельный SPDK            блокировка на запись (последовательно, очень коротко)
```

Внутри `put_restored_batch` I/O SPDK для нескольких объектов отправляется параллельно, а кратковременная последовательность возникает только при финальном обновлении индекса.

#### 4.3.3 Влияние вытеснения на производительность

| Стратегия вытеснения | Влияние на чтение | Влияние на запись | Где применима |
|----------|-----------|-----------|----------|
| LRU | нет (`last_access` при чтении обновляется через AtomicI64) | нет | универсально |
| LFU | нет (при чтении атомарно инкрементируется счётчик) | нет | концентрация горячих данных |
| скан TTL | нет (отдельная фоновая задача) | нет | очистка просроченной разморозки |
| вытеснение по ёмкости | **незначительно** (блокировка на запись RwLock удаляет записи индекса) | **незначительно** | при приближении к пределу ёмкости |

**Важно**: вытеснение выполняется в отдельной фоновой задаче; после пакетного удаления `eviction_batch_size` Blob индекс обновляется одним проходом, что сокращает число блокировок на запись.

### 4.4 Производительность слоя планирования (05)

#### 4.4.1 Конвейер записи при архивации

```
┌───────────┐  ┌───────────┐  ┌───────────┐  ┌───────────┐
│ Stage 1   │  │ Stage 2   │  │ Stage 3   │  │ Stage 4   │
│ чтение    │─▶│ сериализа-│─▶│ двойная   │─▶│ запись на │
│ объекта   │  │ ция+Header│  │ буфериза- │  │ ленту     │
│           │  │           │  │ ция       │  │           │
└───────────┘  └───────────┘  └───────────┘  └───────────┘
     │              │              │              │
 hot-хранилище/   построение    чередование    запись
 кэш,             ObjectHeader  записи в       накопителем,
 асинхронное                     Buffer A/B     последовательное
 чтение                                         дополнение
```

**Механизм двойной буферизации**:

```rust
pub struct ArchiveWritePipeline {
    buffer_a: DmaBuf,          // 64-128MB
    buffer_b: DmaBuf,          // 64-128MB
    active: AtomicBool,        // true=A, false=B
    block_size: usize,         // 256KB
}
```

| Фаза | Buffer A | Buffer B |
|------|----------|----------|
| T1 | заполнение данными объектов | запись предыдущей пачки на ленту |
| T2 | запись на ленту | заполнение данными объектов |
| T3 | заполнение данными объектов | запись на ленту |

**Выгода**: ленточный накопитель пишет непрерывным потоком, без пауз ожидания, пропускная способность близка к теоретическому пределу накопителя.

#### 4.4.2 Количественная выгода объединения восстановлений

| Сценарий | Без объединения | С объединением | Выгода |
|------|--------|--------|------|
| 10 объектов в одном Bundle | 10 перестановок ленты + 10 seek | 1 перестановка + 1 последовательное чтение | **10x** |
| 20 объектов на 3 лентах | 20 перестановок | 3 перестановки + 3 последовательных чтения | **6-7x** |
| 100 объектов на одной ленте в разных Bundle | 100 перестановок + 100 seek | 1 перестановка + N seek через FSF | **~50x** |

Окно объединения `merge_window_secs` (по умолчанию 60s) — это **компромисс между задержкой и пропускной способностью**:
- чем больше окно: тем выше доля объединений и пропускная способность, но растёт задержка первого запроса
- чем меньше окно: тем быстрее ответ, но ниже доля объединений и чаще перестановки лент

#### 4.4.3 Параллельная работа нескольких накопителей

```
Пул накопителей: [Drive 0] [Drive 1] [Drive 2] [Drive 3]
                    │          │          │          │
                    ▼          ▼          ▼          ▼
               Archive     Archive     Recall     Recall
               Bundle A    Bundle B    Job X      Job Y
               (Tape001)  (Tape002)  (Tape003)  (Tape004)
```

| Конфигурация | archive_drives | recall_drives | expedited_reserved |
|------|---------------|---------------|-------------------|
| 4 накопителя, баланс | 2 | 2 | 1 (резерв из recall) |
| приоритет записи | 3 | 1 | 0 |
| приоритет восстановления | 1 | 3 | 1 |
| динамическая настройка | общий пул, конкуренция по приоритету | — | 1 |

### 4.5 Производительность слоя лент (06)

#### 4.5.1 Максимальная последовательность I/O

| Оптимизация | Реализация | Описание |
|------|------|------|
| запись с выравниванием по блоку | данные дополняются до `block_size` (256KB) | меньше внутренних фрагментов и сбросов буфера накопителя |
| крупноблочная запись | каждый `write()` пишет полный блок | исключает микропаузы накопителя от мелких I/O |
| позиционирование по FileMark | `MTFSF` пропускает весь Bundle | в 100 раз быстрее потактового seek |
| позиционирование внутри блока | `MTFSR` пропускает блоки | точное позиционирование объекта внутри Bundle |
| аппаратное сжатие | аппаратное сжатие LTO (настраивается) | эффективная ёмкость выше в 2-3 раза, CPU не задействован |

#### 4.5.2 Оптимизация перестановки ленты

```
Процесс перестановки:
  unload(current_tape)         ~15s  ─┐
  перемещение манипулятора     ~10s   ├─ итого 30s-120s
  load(new_tape)               ~15s   │
  locate/rewind                ~5s   ─┘
```

**Стратегии сокращения перестановок** (по приоритету):

1. **Объединение по ленте**: слой планирования объединяет задачи с одинаковым tape_id в один TapeReadJob
2. **Аффинность к ленте**: планировщик архивации сначала использует оставшееся место уже загруженной ленты
3. **Предварительная загрузка**: если tape_id следующей задачи известен, unload/load выполняются заранее
4. **Удержание накопителя**: после чтения лента остаётся в накопителе некоторое время (`tape_hold_secs`), ожидая запросов на ту же ленту
