# Обзор документации ColdStore

Документы в этом каталоге переработаны по принципу «приоритет отдан текущей реализации, целевой проект сохранён отдельным слоем».

## Актуальные авторитетные документы

| Документ | Назначение |
|------|------|
| [ARCHITECTURE.md](./ARCHITECTURE.ru.md) | Компоненты, обязанности, взаимосвязи и границы согласованности текущей кодовой базы |
| [DESIGN.md](./DESIGN.ru.md) | Более полный исторический документ по проектированию, включает описание целевого состояния; часть материалов может опережать текущую реализацию |
| [plans/](./plans/) | Поэтапные планы внедрения и журнал эволюции |
| [BUILD.md](./BUILD.md) | Правила сборки, линтинга и тестирования: тулчейн, системные пакеты, работа в Docker, критерий готовности, диагностика ([этот файл](./BUILD.ru.md)) |

## Документы по проектированию модулей

Документы в каталоге [modules/](./modules/) сохранены как послойный справочник по проектированию. Они содержат часть материалов о целевом состоянии: настоящий многоузловой Raft, полный SPDK, реальная ленточная библиотека, Admin Console и полное подключение OpenTelemetry.

Приоритет чтения:

1. Сначала прочитайте [ARCHITECTURE.md](./ARCHITECTURE.ru.md), чтобы понять текущую реализацию.
2. Затем прочитайте [modules/README.ru.md](./modules/README.ru.md), чтобы найти целевое проектирование нужного модуля.
3. При вопросах о реализации ориентируйтесь на `crates/*/src` и `crates/proto/proto`.

## Сводка текущего состояния реализации

| Компонент | Текущее состояние |
|------|----------|
| Gateway | Шлюз Axum S3 HTTP; все бизнес-запросы перенаправляются в Scheduler |
| Scheduler | Центр бизнес-оркестрации: PUT/GET/Restore/List, сканирование архивации, планирование восстановления |
| Metadata | Одноузловой путь надёжно сохраняемого конечного автомата; многоузловой `persistent_raft` сейчас работает в режиме fail-fast, чтобы не имитировать псевдокластер |
| Cache | Двухзонный кэш staging/restored: бюджет ёмкости, вытеснение из restored, backpressure в staging |
| Tape | Абстракция TapeService с имитационными и базовыми интерфейсами; интеграция с реальным оборудованием остаётся целевым состоянием |
| Proto | Контракт gRPC уже включает атомарный интерфейс фиксации архивации `CompleteArchiveObject` |

## Важные ограничения согласованности

- `Staging` — это данные пути записи; вытеснение по ёмкости для них недопустимо. При превышении бюджета обязателен backpressure.
- `Restored` — это кэш, который можно пересоздать; допустимо освобождение по LRU/LFU/TTL/ёмкости.
- Завершение архивации в Scheduler необходимо фиксировать одной командой `CompleteArchiveObject` в Metadata; нельзя разбивать её на несколько безусловных RPC.
- Metadata по умолчанию сейчас одноузловая; адрес metadata в worker по умолчанию тоже одноузловой.
- Многоузловая репликация Metadata ещё не завершена, поэтому многоузловую конфигурацию `persistent_raft` нельзя считать готовой для продакшена.
